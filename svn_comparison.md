## 1. Почему в Git ветвление «дешёвое», а в SVN — «дорогое»?

В Git ветка представляет собой лёгкую ссылку на определённый коммит. Создание новой ветки практически не требует копирования файлов и занимает очень мало ресурсов. Кроме того, большинство операций с ветками выполняется локально, поэтому для их создания не требуется подключение к серверу.

В SVN ветвление обычно связано с операциями в центральном репозитории. Традиционно для создания ветки используется копирование каталога в репозитории (`svn copy`), что делает ветвление более зависимым от сервера и сети. Поэтому работа с большим количеством веток в SVN менее удобна и условно считается «дороже», чем в Git.

## 2. Можно ли в SVN сделать коммит без интернета? Почему?

Нет, обычный коммит в SVN без подключения к серверу выполнить нельзя.

SVN использует централизованную модель контроля версий: рабочая копия находится на компьютере разработчика, но история изменений и сам репозиторий хранятся на центральном сервере. При выполнении `svn commit` изменения отправляются непосредственно в центральный репозиторий.

В Git коммит создаётся локально, поэтому его можно сделать без интернета. В SVN без доступа к серверу можно подготовить и изменить файлы, но выполнить полноценный коммит в репозиторий нельзя.

## 3. В каких сценариях SVN до сих пор может быть предпочтительнее Git?

SVN может быть предпочтительнее Git в проектах, где удобнее централизованная модель контроля версий и требуется строгий контроль над репозиторием.

- в крупных организациях с уже существующей инфраструктурой SVN;
- в проектах, где необходимо централизованно контролировать доступ к файлам и изменениям;
- при работе с большими бинарными файлами и некоторыми видами медиа- или игровых ресурсов;
- в старых корпоративных системах, которые уже тесно интегрированы с SVN;
- в командах, которым не нужны сложные распределённые рабочие процессы Git.

Таким образом, Git сегодня чаще выбирают для современной разработки благодаря удобному ветвлению, локальным коммитам и распределённой модели. Однако SVN всё ещё может иметь смысл там, где важны централизованное управление, существующая инфраструктура и совместимость с уже используемыми системами.
